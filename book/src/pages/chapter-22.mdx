# Chapter 22: Implementing Scanners

For developers: keep scanning logic deterministic, configuration-driven, and measurable. OTs need predictable behavior that they can tune; developers need clear parameters with measurable effects.

## Why This Matters

Single-switch scanning performance is dominated by timing, layout, and errors. If the implementation hides or blends those factors, clinicians and developers can’t reliably improve text entry rate (TER). The goal here is a predictable system with explicit settings and instrumentation.

## Settings Optimization (Koester & Simpson 2014)

A structured decision tree improves text entry rate (TER). In seminal clinical research by Heidi Koester and Richard Simpson (2014, *Journal of Rehabilitation Research and Development*), systematically tuning scanning parameters using evidence-based heuristics produced an average **120% increase in Text Entry Rate (TER)** (from a baseline of 1.42 WPM up to 6.51 WPM).

A foundational rule of this clinical model is the **25% scanning error threshold**: if errors exceed 25% of selections, you **must** focus on reducing errors before optimizing speed or layout.

## What You Need to Measure

At minimum, capture three quantitative inputs before attempting to optimize scanning settings:

- **Switch press time** (mean reaction time `RT` and standard deviation `SD`). Use this with the .65 rule (`T_scan = RT ÷ 0.65`) to set a starting scan delay (see Chapter 13).
- **Scanning error rate (%)**: `Error Rate = (Incorrect Selections + Timing Errors) ÷ Total Selections × 100`.
- **Text Entry Rate (TER)**: Measured in words per minute (`WPM = (Characters ÷ 5) ÷ Minutes`).

If you log individual scan step telemetry, you can diagnose whether errors are caused by a **late first press** (scan rate too fast), a **late next press** (inadequate 1st-item delay), **unintentional presses** (insufficient acceptance delay/debounce), or **missed first rows** (manual vs auto initiation issue).

## Decision Branch Summary

Use this as a short-form implementation guide for clinicians and assistive technology developers:

- If **Switch Performance is NOT OK**: revise switch mounting, switch type, or acceptance delay; re-test switch activation consistency before tuning software scanning.
- If **Performance is OK**: run a standardized scan test to compute error rate and baseline TER.
- If **TER cannot improve**: maintain current profile.
- If **Errors &gt; 25%**: apply error-reduction interventions (slower scan delay, 1st-item pause, acceptance delay).
- If **Errors &le; 25%**: apply efficiency improvements (reduce dead time, optimize word prediction list length, switch to frequency-based ETAOIN SHRDLU layout).

## Error-Reduction Interventions

When error rate exceeds 25%, target the specific failure mode:

- **First press too late** → increase scan delay by 15–25% (or set to `RT ÷ 0.65`) and add a 500–1000 ms scan-initiation delay.
- **Next press too late** → add a 250–500 ms 1st-item delay on rows and columns.
- **Unintentional presses / tremors** → increase acceptance delay (+150–300 ms hold window) and enable debounce (50–100 ms).
- **Missing first-row selections** → switch to manual scan initiation or extend 1st-row pause.

These are intentionally conservative changes; once error rate drops below 25%, move to efficiency improvements.

## Efficiency Improvements

Once errors are controlled (Error Rate ≤ 25%), aim for fewer scan steps and less dead time:

- Remove unnecessary scan targets (title bar, window control items).
- Put letters + prediction candidates first; stay in prediction mode until word completion.
- Use a frequency-based letter layout (ETAOIN SHRDLU) unless the user specifically requires an alphabetical board.
- Tune word prediction list size (3–6 candidates); excessively long prediction lists add visual search overhead that negates keystroke savings.

## Implementation Checklist for Developers

- Settings are stored as explicit typed fields and versioned per user profile.
- All timing parameters are displayed in milliseconds (ms) in the UI.
- Each selection event logs: target ID, selected ID, scan delay, step count, and error type.
- The system can replay a scanning session to diagnose error clusters.
- A standardized scan-test mode exists for short, repeatable measurements.
